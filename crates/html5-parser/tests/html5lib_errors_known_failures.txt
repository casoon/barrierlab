# Known-failing html5lib-tests parse-error cases (see
# tests/html5lib_conformance.rs, `html5lib_parse_errors`, and
# tests/html5lib-tests/README.md).
#
# One `<file>#<index>` key per line (same indexing as
# html5lib_known_failures.txt). Regenerate with
# `HTML5LIB_BLESS=1 cargo test --test html5lib_conformance` after
# investigating *why* each entry fails — never hand-add an entry just to
# silence a failure. An entry that starts passing must be removed (the test
# fails on stale entries).
#
# Why the current entries fail, by file:
#
# - tests16.dat (26), domjs-unsafe.dat (9), plain-text-unsafe.dat (3):
#   tokenizer gaps, not tree construction. The tokenizer does not record
#   `unexpected-null-character` in the RCDATA, RAWTEXT, script data and
#   PLAINTEXT states (nor in tag/attribute/comment/DOCTYPE states other than
#   Data), and it does not record `eof-in-script-html-comment-like-text` for
#   an EOF inside `<script><!--` before the escaped states are reached.
# - doctype01.dat (2): the tokenizer does not record
#   `missing-quote-before-doctype-system-identifier` from the "after DOCTYPE
#   public identifier" / "between DOCTYPE public and system identifiers"
#   states ("anything else").
# - html5test-com.dat (6), webkit02.dat (5): these files carry no error
#   expectations at all (empty `#errors`), so every error this crate
#   correctly reports counts as a false positive: EOF inside an unclosed
#   `svg`/`math` (html5test-com), `</button>` closing a `button` that still
#   contains a `selectedcontent` (webkit02, §13.2.6.4.7 "generate implied end
#   tags ... if the current node is not a button element"), plus
#   `cdata-in-html-content` for CDATA inside an HTML integration point
#   (html5test-com#15, #18).
#
# Not compared at all: html5lib's DOCTYPE-shape errors (missing or
# non-conforming DOCTYPE), which this crate deliberately does not record —
# html-conform reports those findings itself.
